# 자동화 동작 명세 (단계 5)

단계 5(자동화)의 동작 기준이다. 스케줄, Slack 알림, 일일 리포트, 봇 토큰 + CI API, 대시보드를 다룬다.
이 문서는 defE2End 가 **사용자에게 보이는 동작과 규칙**을 코드 없이 적는다. 데이터 모델·담당 경계·시험은 [stage5-contract.md](stage5-contract.md) 에 있고, 둘이 다르면 계약 문서를 따른다.

---

## 1. 스케줄

### 1.1 단위·표현
- 스케줄은 **환경 하나**와 대상(시나리오 목록 또는 **태그 하나**)을 가진다. 태그면 발화할 때 그 태그의 보관 안 된 시나리오를 전부 고른다. 실행 방식(`mode`)과 실패 뒤 계속 여부(`continueOnFailure`)는 그룹 실행과 같다.
- 표현은 **5칸 cron**(분 시 일 월 요일). 초 단위는 없다.
- 시간대는 **스케줄마다 IANA 시간대**. 새 스케줄은 워크스페이스 기본 시간대(기본 `UTC`)를 따른다.
- 서머타임으로 없는 시각은 건너뛰고, 두 번 오는 시각은 한 번만 돈다.
- 저장할 때 cron 을 검사한다. 틀린 식과 **영영 돌지 않는 식**(2월 31일 등)은 거부한다. 편집 화면은 다음 5회 실행 시각을 미리 보여 준다. 저장·미리보기·발화는 같은 계산 함수를 쓴다.
- 다음 실행 시각(`nextRunAt`)을 DB 에 저장하고 목록에 보여 준다.

### 1.2 소유·권한
- 만든 사람과 마지막으로 고친 사람을 기록한다. 설정을 바꿀 때마다 버전이 올라가고, 발화 기록에 그때의 버전이 남는다.
- 만들기·고치기·켜기/끄기·지우기와 스케줄 값·세션 관리는 `schedule.write`(편집자 이상). 읽기는 워크스페이스 멤버 누구나(비밀 값은 "값 있음"만 보인다).

### 1.3 발화·실행
- 실행 위치는 **서버만**(headless). 스케줄이 특정 PC 로 가는 경로는 없다.
- worker 의 리더 하나가 15초마다 때가 된 스케줄을 고른다. 스케줄마다 한 트랜잭션에서 행을 잠그고, 켜짐 여부와 `nextRunAt` 을 다시 읽은 뒤 발화한다. 편집도 같은 행을 잠그므로 옛 설정으로 발화하는 일이 없다.
- 발화하면 그룹 실행 하나를 만든다(출처 `schedule`, 요청자 없음). 대상이 0개면 `refused(no_scenarios)`, 생성 오류(빠진 값·세션·상한)는 `refused(<코드>)` 로 기록한다.
- 다음 `nextRunAt` 은 **지금 이후** 첫 예정 시각으로, 같은 트랜잭션에서 저장한다.

### 1.4 중복·겹침·놓침
- **중복 발화 없음**: worker 가 여러 개여도 (스케줄, 예정 시각) DB 유일 키와 행 잠금 때문에 한 예약은 한 번만 돈다.
- **겹침**: 기본은 **건너뛰고 기록**(`skipped_overlap`) — 이 스케줄의 대기·실행 중 실행이 남아 있으면 새로 만들지 않는다. 스케줄마다 "겹쳐도 실행"을 고를 수 있다.
- **놓친 예약**: 예정 시각이 2분 넘게 지났으면 실행하지 않고, 지나간 모든 예정 시각을 `missed` 한 줄(첫 시각·마지막 시각·횟수)로 기록한다. 2분 안이면 가장 이른 시각 하나만 실행하고 나머지는 놓침으로 기록한다.
- 발화 기록(`started`·`skipped_overlap`·`missed`·`refused`·`error`)은 스케줄 화면에서 볼 수 있다.

### 1.5 스케줄 값과 로그인 세션
- 스케줄은 사람의 개인 값·세션을 쓰지 않는다. 대상 환경의 **개인 변수마다 스케줄 전용 값**을 넣는다(비밀이면 암호화·쓰기 전용). 공유 변수는 환경 값을 쓴다.
- `useAuthSession` 환경이면 스케줄 **전용 로그인 세션**을 앱의 캡처 창으로 만든다.
- 발화 때 필요한 스케줄 값이나 세션이 없으면 실행하지 않고 `refused(variable_missing|auth_session_missing)` 로 기록·알림한다. 사람의 값·세션으로 넘어가지 않는다.
- 스케줄의 환경을 바꾸면 스케줄 값은 지워진다(확인 후). 변수가 개인→공유로 바뀌거나 비밀 표시가 바뀌어도 전용 값은 지워진다.
- 바꾼 사람·시각은 감사 기록에 남는다(값 없이).
- 신뢰 모델: 편집 권한이 있는 사람은 시나리오 스텝을 고칠 수 있고, 스케줄은 그 스텝을 전용 값으로 돌린다. 스텝을 악의로 바꿔 값을 빼내는 것은 같은 조직 안의 신뢰로 다루며 막는다고 약속하지 않는다.

### 1.6 재시도
- 단계 3 의 실행 전체 재시도 규칙을 그대로 쓴다.

## 2. Slack 알림

### 2.1 저장·범위
- 워크스페이스에 Incoming Webhook 을 **여러 개** 둘 수 있다(이름, 알림 조건, 출처, 리포트 설정). 관리는 `notification.write`(관리자).
- 웹훅 URL 은 **암호화** 저장하고 화면에는 끝 4자만 보인다. URL 원문은 어떤 응답·로그·감사 기록·알림 본문에도 나오지 않는다.

### 2.2 언제 보내나
- 실행 출처(`schedule`·`api`·`manual`)가 웹훅의 출처 목록에 있을 때, 알림 조건에 따라:
  - `all`: 모든 종료.
  - `failures`: 통과가 아닌 것(경고가 있는 `passed` 포함).
  - `changes`: 같은 시나리오·환경의 직전 종료 실행과 상태가 다를 때.
- 그룹 실행은 **한 통**(요약 + 실패 목록 최대 10개). 그룹 자식은 따로 보내지 않는다.
- 시험 실행과 사람이 취소한 실행은 보내지 않는다.
- 스케줄 발화가 `refused`·`error`·`missed` 면 사유 코드와 고칠 곳 링크를 담아 보낸다(출처에 `schedule` 이 있을 때).
- 실행이 종료되는 모든 경로(worker 판정, 점유 만료 정리, 취소, 그룹 집계, 데스크톱 완료·대조)가 같은 트랜잭션에서 배달 여부를 정한다.

### 2.3 메시지
- 상태, 대상 이름, 환경, 출처(스케줄 이름·봇 이름·사람), 소요 시간, 실패 스텝 번호·이름·사유(비밀 값은 가림), 결과 링크.
- 결과 링크는 `PUBLIC_URL` 이 있을 때만 붙는다. 언어는 워크스페이스 설정(기본 영어).

### 2.4 보내기·재시도
- 알림은 DB 대기열에 쌓이고, 리더 하나가 5초마다 점유해 보낸다. 재시작해도 대기열이 남는다.
- 요청 제한 시간 10초. **총 4회 시도**(재시도 간격 5초·30초·120초). 5xx·네트워크 오류·시간 초과는 다음 시도, 다 쓰면 `failed`.
- 429 는 `Retry-After`(최대 10분)를 따르되 같은 횟수 안에서.
- 4xx(429 제외)는 바로 포기하고 그 웹훅을 **무효**로 표시한다. 설정 화면에 무효 표시가 보인다.
- **시도마다** 기록(시각·소요 시간·상태 코드 또는 오류 코드, URL·값 없이)을 남긴다.
- 외부 전송은 **최소 한 번**이다. Slack 이 받은 직후 기록 전에 프로세스가 죽으면 같은 알림이 한 번 더 갈 수 있다.
- 알림 실패는 실행 결과를 바꾸지 않는다.
- 테스트 전송: 그 웹훅으로만, 대기열 없이 바로 보내고 결과를 화면에 보여 준다(시도 기록은 남긴다).

## 3. 일일 리포트

- 웹훅마다 켜고, 보낼 시각과 시간대를 정한다.
- 집계 창은 **직전 리포트 이후**의 고정 창 `[from, to)` 이다(첫 리포트는 24시간). 주말·휴일을 건너뛰어도 빠지는 실행이 없다. 같은 창은 두 번 만들지 않는다(리더가 여럿이어도).
- 내용: 실행 수, 통과율, 상태별 수, 새로 실패한 시나리오, 연속 실패(2회 이상), 놓친·건너뛴·거절된 예약 수, 대시보드 링크. 시험 실행은 뺀다.
- 실행이 0건이면 "실행 없음" 한 줄을 보낸다. 켜진 스케줄이 있는데 0건이면 그 사실을 강조한다.
- 보내기·재시도는 2.4 와 같다.

## 4. 봇 토큰 + CI API

### 4.1 토큰
- 관리자가 **웹 화면**에서 만든다: 이름, 범위(`runs:create`·`runs:read`·`runs:cancel`), 만료(기본 90일, 최대 365일, **필수**).
- 원문 `d2e_<랜덤>` 은 만들 때 **한 번만** 보여 주고, DB 에는 SHA-256 해시만 둔다. 목록은 이름·앞 8자·범위·만료·마지막 사용·만든 사람.
- 폐기하면 즉시 무효. 마지막 사용 시각은 1분에 한 번 이하로 갱신한다.
- 토큰은 자기 워크스페이스 자원만 다룬다(그 밖은 404). 봇 토큰은 `/api/v1` 전용이고 MCP 에서는 쓰지 않는다.

### 4.2 봇 값과 세션
- 봇 실행은 **봇 토큰 전용 값과 전용 로그인 세션**으로 돈다(1.5 와 같은 규칙, 토큰은 여러 환경에 쓸 수 있으므로 변수 단위). 요청자는 없고 출처에 봇 토큰이 기록된다.
- 필요한 값이나 세션이 없으면 `409`(`variable_missing`·`auth_session_missing`). 사람의 값·세션으로 넘어가지 않는다.
- 실행 위치는 **서버만**.

### 4.3 `/api/v1`
- 헤더 `Authorization: Bearer d2e_…`. 웹 UI API 와 분리된 고정 형식이다.
- `POST /api/v1/runs`: 시나리오 하나, 시나리오 목록, 또는 태그로 실행을 만든다. `Idempotency-Key` 헤더 필수(1~128자). 같은 토큰·같은 키·같은 본문이면 처음 만든 실행을 돌려주고(태그면 처음 고른 대상 그대로), 본문이 다르면 `409 idempotency_conflict`. 키는 24시간 유지된다. 다른 토큰의 같은 키는 서로 무관하다.
- `GET /api/v1/runs/{id}?wait=<초>`: 최대 60초 기다렸다 돌려준다. 기다리는 동안 토큰 폐기·만료를 계속 확인한다. 동시 대기가 토큰당 5·전체 100을 넘으면 `429 too_many_waits`.
- `POST /api/v1/runs/{id}/cancel`.
- 응답 `{ id, kind, status, startedAt, finishedAt, warningCount, url, children? }`, 오류 `{ error: { code, message } }`.
- **CI 는 `passed` 만 통과**로 본다. 예시는 [ci.md](ci.md).

## 5. 대시보드

- 기간 7·30·90일, 사이트·환경 필터. 날짜 경계는 워크스페이스 시간대.
- 카드: 통과율(취소 제외), 실행 수, 평균 소요 시간, 지금 실패 중 수, 놓친·건너뛴·거절된 예약 수.
- **지금 실패 중**: 시나리오×환경의 마지막 실행이 통과가 아닌 것을 분류한다.
  - 신규: 직전 실행은 통과.
  - 연속: 2회 이상 연달아 실패.
  - 간헐: 최근 5회 안에 통과와 실패가 섞임.
  - 같은 실패 스텝·사유가 3개 이상이면 한 묶음으로 보여 준다.
- 일별 통과율 추이, 실패 많은 시나리오 상위 10개(기간 안 3회 이상 실행).
- 시험 실행은 뺀다.
