# 단계 8 계약 — 1.0 배포

> 2026-10-16. 단계 8(문서·이미지와 앱 배포·공개 전 점검)을 여러 사람이 나눠 만들 때 맞춰야 하는 결정. 바꾸려면 이 문서부터 고친다.
> 상위 문서: [plan.md](plan.md) 1절(앱 배포·책임 경계)·6절(업그레이드·백업·버전)·8절·9절(공개 전 점검). 같은 날 구현 전 검토(10건)를 반영했다.

## 0. 완료 기준 (plan 8절)

- **신규 설치**: 빈 PC 에서 문서대로 `docker compose` 로 서버를 띄우고 첫 관리자를 만들 수 있다.
- **업그레이드**: 이전 버전 이미지로 데이터를 만든 뒤 새 버전으로 올려도 데이터가 남고 동작한다(CI 시험).
- **백업·복원**: 백업 명령으로 만든 묶음을 빈 환경에 복원하면 같은 데이터가 보인다(CI 시험, 릴리스마다).
- **실제 다운로드 파일 설치**: GitHub Releases 에서 받은 mac·Windows 설치 파일을 깨끗한 PC 에 설치해 실행하고 서버에 연결한다(사람이 하는 시험, 체크섬 확인 포함).

## 1. 결정

| 항목 | 결정 |
|---|---|
| 버전 | 저장소 하나에 버전 하나(semver). 첫 정식은 `1.0.0`, 그 전 시험 릴리스는 `1.0.0-rc.N`. 버전의 출처는 git 태그 `vX.Y.Z` — 릴리스 빌드가 태그에서 읽어 앱·서버·runner·MCP 에 새긴다 |
| 서버 이미지 | `ghcr.io/97kim/defe2end-web`, `-worker`, `-migrate`. linux/amd64·arm64. 태그는 **정확한 버전 `X.Y.Z`(시험은 `X.Y.Z-rc.N`) 하나만** — `X.Y`·`latest` 는 두지 않는다. 이미 있는 버전 태그는 덮어쓰지 않는다(작업이 먼저 확인하고 멈춘다). 세 이미지는 같은 커밋·같은 작업에서 만든 묶음이다 |
| compose | `deploy/docker-compose.yml` 은 이미지 기반(`DEFE2END_VERSION` 하나로 세 이미지를 같은 정확한 버전에 고정, 기본값 없음). 소스에서 빌드하는 구성은 `deploy/docker-compose.build.yml` 로 옮긴다(개발·CI 용) |
| 앱 | mac(dmg, arm64·x64 각각), Windows(nsis, x64). **서명 없음**. 자동 업데이트 없음 |
| 새 버전 알림 | 앱이 **시작 60초 뒤**와 하루 한 번 GitHub Releases 공개 API 로 최신 정식 릴리스를 확인해, 더 새 버전이면 알림(다운로드 페이지 링크). 요청에는 인증·서버 주소·사용자 식별자를 싣지 않는다(공개 API 라 IP 는 GitHub 에 전달됨을 문서에 밝힘). 시간 제한 5초, 실행을 막지 않음, 실패는 조용히. 설정에서 끌 수 있고 첫 확인 전(60초 안)에도 끌 수 있다. 시험 릴리스(`-rc`)는 알리지 않는다 |
| 릴리스 작업 | 두 단계. ① `vX.Y.Z[-rc.N]` 태그 push(형식 검사, 태그 커밋이 `main` 에 있어야 함, 같은 버전 릴리스가 이미 있으면 멈춤): 전체 시험 → 이미지를 **커밋 태그(`sha-<커밋>`)로만** 올려 digest 를 기록 → 앱 빌드 → SBOM·고지·체크섬·출처 증명 → **초안 릴리스**(digest 목록 포함). 이 단계에서는 버전 태그가 붙은 이미지가 공개되지 않는다. ② 사람이 초안을 확인한 뒤 수동 실행(`workflow_dispatch`, 버전 입력)으로 **같은 digest** 에 버전 태그를 붙이고 릴리스를 게시한다. 쓰기 권한(`packages: write`·`contents: write`·`id-token`·`attestations`)은 그 권한이 필요한 작업에만, 모든 action 은 커밋 SHA 로 고정, 포크 PR 의 산출물·캐시는 릴리스에 쓰지 않는다 |
| SBOM·고지 | 배포물마다 CycloneDX SBOM 과 제3자 고지. npm 의존성만이 아니라 **최종 이미지의 OS 패키지·글꼴·네이티브 바이너리**와 앱에 동봉한 파일(Electron·Chromium·ffmpeg 등)까지 대조한다. 원본 NOTICE·저작권 문구를 그대로 싣고, 소스 제공 의무가 있는 구성 요소(LGPL 등)는 따로 확인해 고지에 적는다. 이미지는 `/licenses/` 에, 앱은 리소스 폴더에, 릴리스 자산으로도 올린다 |
| 체크섬·출처 증명 | 릴리스 자산 전체의 `SHA256SUMS` 와 GitHub 출처 증명(이미지 digest·설치 파일). 문서에 `gh attestation verify` 검증 명령. 서명 없는 앱의 열기 안내는 "공식 릴리스에서 받았고 검증이 성공한 파일"에만 해당한다고 적는다 |
| 백업 | migrate 이미지에 `backup`·`restore` 명령. 대상: DB 덤프 + 파일 저장소 + 설정 확인 목록. **web·worker 를 멈춘 상태에서만** 백업한다(앱 연결이 남아 있으면 거부) — 실행 중에는 정리 작업·삭제가 파일을 지워 덤프와 어긋날 수 있다. **암호화 키는 묶음에 넣지 않는다**(따로 보관 안내). 대신 키 확인 값(키로 만든 HMAC)을 manifest 에 넣어 복원 때 맞는 키인지 검사한다 |
| 업그레이드 시험 | CI 에서 이전 정식 릴리스 이미지(없으면 기준 커밋 `6dbe822` 의 소스로 빌드한 이미지)로 **그 버전의 코드가** 데이터를 만든 뒤 지금 버전으로 바꾸고 로그인·실행·비밀 값 복호화·파일 접근까지 확인 |
| 호환 | 앱과 서버: 주 버전이 같고 앱의 부 버전 ≥ 서버의 부 버전 − 1(plan 6절의 N-1 = 부 버전). 실제 실행 가능 여부는 지금처럼 프로토콜 버전·기능 목록 검사가 판정한다. 서버 안(web·worker·migrate): web·worker 는 시작할 때 DB 의 마이그레이션 목록이 자기 이미지가 아는 목록과 정확히 같아야 뜬다(모르는 마이그레이션이 있거나 빠졌으면 이유를 남기고 종료) — 버전이 섞인 배포를 막는다 |
| 문서 | `docs/guide/`(영어)와 `docs/guide/ko/`(한국어). 설치·설정·업그레이드·백업과 복원·데스크톱 앱·AI 연결·보안과 한계·최소 사양·문제 해결. README 에 빠른 시작 |
| 최소 사양 | 측정 전 값은 "추정"으로 표시(plan 6절) |

## 2. 문서 (`docs/guide` — 문서 담당)

- **설치**: 필요한 것(Docker·Compose 버전), `.env` 만들기(키 생성 명령 포함), `docker compose up -d`, 첫 관리자, HTTPS 는 사용자 몫(리버스 프록시 예시는 짧게, 특정 클라우드 이름 없이).
- **설정**: 모든 환경 변수 표(이름·필수 여부·기본값·설명). 코드에서 실제로 읽는 변수와 일치해야 한다(문서 담당이 코드에서 목록을 뽑아 대조).
- **업그레이드**: 버전 바꾸기, 업그레이드 전 백업, 건너뛰기 경로는 릴리스 노트에서 확인.
- **백업과 복원**: 4절 명령 사용법, 키 따로 보관, 빈 환경 복원 순서.
- **데스크톱 앱**: 다운로드·체크섬 확인·설치. 서명이 없어 처음 실행 때 OS 가 막는 경우의 정상적인 열기 방법(mac 의 "시스템 설정 > 개인정보 보호 및 보안 > 그래도 열기", Windows SmartScreen 의 "추가 정보 > 실행")만 안내하고, 보안 기능 전체를 끄라고 안내하지 않는다. 회사 정책으로 막히는 환경이 있음을 밝힌다. 서버 연결, 새 버전 알림 끄기.
- **AI 연결**: 지원하는 CLI 와 확인한 버전, 앱 채팅이 defE2End 도구만 쓰는 이유와 한계, 모델 요청은 외부로 나간다는 점, MCP 등록.
- **보안과 한계**: 비밀 값 암호화와 키, 마스킹이 가리지 못하는 것(`docs/masking.md` 연결), 같은 OS 사용자 프로세스에 대한 한계, Windows 파이프 권한 상태.
- **문체**: 영어는 짧고 직접적으로, 한국어는 조사를 붙여 쓰고 해라체로 끝내지 않는다. 특정 회사·서비스 이름을 쓰지 않는다(공개 연습용 사이트 예시는 괜찮다).

## 3. 릴리스 파이프라인 (`.github/workflows/release.yml` 등 — 배포 담당)

- 태그에서 버전을 읽어 각 패키지에 새기는 스크립트(빌드 산출물에만, 커밋하지 않음). 앱의 `app.getVersion()`, 서버의 버전 응답, runner·MCP 버전이 같은 값.
- 이미지: buildx 다중 아키텍처, GHCR 게시(`GITHUB_TOKEN` 의 `packages: write` — 이 작업에만 권한), 이미지 라벨(OCI source·version·revision), `/licenses/` 에 SBOM·고지.
- 앱: mac arm64·x64 dmg, Windows x64 nsis. 리소스에 SBOM·고지. 서명 관련 환경 변수는 비워 둔다.
- SBOM 은 CycloneDX(도구는 판단 — 오프라인 재현 가능하고 라이선스가 자유로운 것). 제3자 고지는 SBOM 에서 라이선스 본문을 모아 만든다.
- `SHA256SUMS`, 초안 릴리스(자산 전부, 릴리스 노트 초안). 태그가 `-rc` 면 시험 릴리스(prerelease)로.
- 기존 `ci.yml` 은 그대로 두되, 수동 실행의 설치 파일 업로드는 유지.
- 새 버전 알림(1절)을 앱에 구현한다(설정 저장·끄기, 정식만, 실패 조용히, 시험).
- 공개 점검: 릴리스 산출물(이미지 파일 목록·앱 리소스)에 클린룸 검사를 돌리는 단계를 넣는다(CI 비밀 값 `CLEANROOM_HASHES`).

## 4. 백업·복원·업그레이드 (`packages/db` 또는 migrate 이미지 — 운영 담당)

- `backup <디렉터리>`: **web·worker 가 멈춰 있어야 한다** — DB 에 앱 연결(이름으로 구분)이 남아 있으면 거부하고 `docker compose stop web worker` 를 안내. DB 덤프(`pg_dump` 사용자 정의 형식) → 파일 저장소 묶음 → `manifest.json`(앱 버전, 마이그레이션 이름과 체크섬 목록, 만든 시각, 필요한 환경 변수 **이름** 목록, 파일마다 경로·크기·SHA-256, 덤프 SHA-256, **키 확인 값**: 암호화 키로 만든 고정 문자열의 HMAC). 키·비밀 값은 넣지 않는다.
- `restore <디렉터리>`: 사전 검사를 모두 통과해야 시작한다 — 빈 DB·빈 저장소(아니면 거부, 강제 옵션 없음), manifest 의 버전·마이그레이션 체크섬이 지금 이미지와 같음(다르면 같은 버전으로 복원 뒤 업그레이드하라고 안내), 덤프·파일 해시 일치, 키 확인 값이 지금 키와 맞음(다르면 거부. 키를 잃은 경우에만 `--without-key` 로 복원하고, 그때 비밀 값·웹훅·로그인 세션은 읽을 수 없는 상태로 표시하고 다시 입력하라고 안내). 시작할 때 "복원 중" 표시를 남기고 끝나면 지운다 — 표시가 남아 있으면 web·worker 는 뜨지 않는다(반쯤 복원된 환경으로 돌지 않게).
- **복원 뒤 격리**: 복원은 **자동화 정지 상태**로 끝난다 — 스케줄·알림 배달·대기 중 실행을 돌리지 않고, 복원된 실행 점유·진행 중 실행은 오류(복원으로 중단)로, 대기 중 알림 배달은 취소로 정리한다. 운영자가 확인한 뒤 `resume-automation` 명령(또는 관리자 화면)으로 재개한다. 원본이 이미 처리한 작업을 복원본이 다시 실행하지 않게 하려는 것이다.
- **CI 시험**: compose(소스 빌드 구성)로 띄워 데이터(관리자·워크스페이스·시나리오·실행·산출물 파일·비밀 변수·스케줄)를 만들고 → web·worker 정지 → 백업(앱이 떠 있으면 거부되는지도) → 빈 환경에 같은 키로 복원 → 자동화가 멈춰 있는지 → 재개 → 데이터·파일·비밀 값 확인. 다른 키로 복원하면 거부, `--without-key` 면 비밀 값이 읽을 수 없음으로 표시되는지. 중간 실패 시뮬레이션 뒤 web 이 뜨지 않는지.
- **업그레이드 시험**: 1절 결정대로 기준 커밋(첫 공개 커밋 `6dbe822`, 이후에는 이전 정식 릴리스)의 **소스로 빌드한 이미지**로 띄워 그 코드의 API 로 데이터를 만들고, 지금 버전 이미지로 바꿔 migrate → 로그인·실행 한 번·비밀 값 복호화·파일 접근 확인.
- **버전 섞임 거부**: web·worker 시작 검사(1절 호환)와 시험.

## 5. 사람이 하는 시험 (리드·사용자)

- 깨끗한 mac 에서 실제 다운로드 파일 설치·실행·연결·실행 한 번, 수동 업데이트(새 버전 설치) 한 번.
- 깨끗한 Windows PC 에서 같은 시험 + Windows 파이프 권한 확인(단계 6 에서 미룬 것). **Windows PC 가 필요하다.**
- 게시: 초안 릴리스 확인 → 게시(사용자에게 묻고).
